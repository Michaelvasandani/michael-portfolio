# Terminal-oriented frontend options for a static-first Vercel portfolio

Research date: 2026-08-24

## Question

Which maintained frontend frameworks and terminal-oriented UI libraries are credible prototype candidates for a TypeScript portfolio that deploys to Vercel, renders useful semantic content without JavaScript, adds a lightweight command transcript with clickable and keyboard-operable choices, respects reduced-motion preferences, gives content stable URLs, and consumes repository-maintained JSON at build time?

This report compares options and recommends a short prototype set. It deliberately does **not** select the final architecture.

## Answer in brief

The requested experience is not a terminal emulator. It is a content website with a terminal visual language and a progressively enhanced command chooser/transcript. Those layers should remain separate:

1. A static generator renders the complete portfolio and generated JSON into HTML at build time.
2. Native links and buttons remain the semantic interaction surface.
3. A CSS system supplies the terminal look.
4. A small TypeScript or framework component enhances command selection and transcript behavior when JavaScript is available.

On that basis, the most useful prototype combinations are:

1. **Astro static output + native HTML + a small TypeScript enhancement + selected WebTUI CSS modules.** This tests the lowest-runtime implementation with the clearest no-JS story. Astro prerenders by default, its components ship no client runtime unless explicitly hydrated, it imports JSON directly, and static Astro sites deploy to Vercel without an adapter. [Astro on-demand rendering](https://docs.astro.build/en/guides/on-demand-rendering/), [Astro islands](https://docs.astro.build/en/concepts/islands/), [Astro JSON imports](https://docs.astro.build/en/guides/imports/#json), [Astro deployment to Vercel](https://docs.astro.build/en/guides/deploy/vercel/)
2. **Astro static output + one React island + `cmdk` + selected WebTUI CSS modules.** This tests whether a well-known React command-menu primitive materially improves keyboard discovery and filtering while leaving the portfolio body static. Astro supports React islands without hydrating the rest of the page; `cmdk` describes itself as an accessible, unstyled combobox/command menu, supports arrow-key selection, and is a client component. [Astro islands](https://docs.astro.build/en/concepts/islands/), [`cmdk` repository](https://github.com/dip/cmdk)
3. **Next.js static export + React + `cmdk` + selected WebTUI CSS modules.** This tests the all-React alternative and the largest component ecosystem. Next can emit an HTML file per route with `output: 'export'`, prerenders Client Components to HTML, and runs Server Components during the build, but the React/client-component path is a broader runtime and framework commitment than this portfolio intrinsically needs. [Next.js static exports](https://nextjs.org/docs/app/guides/static-exports), [Next.js SPA/static-export comparison](https://nextjs.org/docs/app/guides/single-page-applications)

Use a plain **Vite + HTML + TypeScript** version as a useful simplicity control if prototype time permits. Vite natively handles TypeScript and JSON and Vercel detects it, but Vite alone is not an HTML content generator: either the present build script must grow into one or the JSON must be fetched in the browser, which would violate the useful-no-JS requirement. [Vite features](https://vite.dev/guide/features.html), [Vite static deployment](https://vite.dev/guide/static-deploy.html#vercel)

WebTUI is the best current styling library to test, not a drop-in accessibility solution. Its package is a modular CSS library with native-element examples and zero JavaScript dependencies, and its current repository/package activity is recent. However, its base stylesheet globally removes outlines and applies `word-break: break-all`; its text input stylesheet does not add a replacement focus treatment. A prototype must import narrowly or override those rules and add a consistent `:focus-visible` design. [WebTUI repository](https://github.com/webtui/webtui), [WebTUI base CSS](https://github.com/webtui/webtui/blob/master/packages/css/src/base.css), [WebTUI input CSS](https://github.com/webtui/webtui/blob/master/packages/css/src/components/input.css), [WebTUI npm metadata](https://registry.npmjs.org/@webtui%2Fcss/latest)

Do not use xterm.js or another full emulator merely to produce the aesthetic. xterm.js is a strong, actively maintained terminal emulator with screen-reader and contrast options, but it implements terminal buffers, VT sequences, input/output, rendering, and optional PTY connections. That is a different problem from navigating static portfolio content and would make the no-JS fallback a separate implementation. [xterm.js repository](https://github.com/xtermjs/xterm.js), [xterm.js terminal options](https://xtermjs.org/docs/api/terminal/interfaces/iterminaloptions/)

## Evaluation criteria

The comparison gives extra weight to properties that protect the agreed product boundary:

- **Static-first:** every About, Experience, Projects, Recent Work, and Maintainer fact appears in generated HTML before client JavaScript runs.
- **Progressive enhancement:** without JavaScript, command choices are real links to routes or fragments and the full content remains readable. With JavaScript, selection can append or reveal transcript entries.
- **Semantic interaction:** navigation uses `<a href>`, actions use `<button>`, and text entry—if retained—has a visible `<label>`. The terminal metaphor does not replace browser semantics.
- **Keyboard and assistive technology:** visible focus, normal Tab order, Enter/Space activation, and an announced dynamic transcript are explicit acceptance criteria rather than assumptions inherited from a library.
- **Reduced motion:** cursor blinking, typing simulations, auto-scroll, and transcript transitions are disabled or shortened under `prefers-reduced-motion: reduce`.
- **Addressability:** important content has stable routes or fragment identifiers that work on initial load, refresh, Back/Forward, copy/paste, and no-JS navigation.
- **Simple production:** static files on Vercel; no database, authentication, server function, visitor shell, or client-side content API.
- **Repository-backed content:** `_data/profile.json`, `_data/generated/projects.json`, and `_data/generated/recent-work.json` are validated and consumed at build time, so the Portfolio Maintainer remains the source of generated facts.

### Framework conclusion

Astro is the most informative prototype host because it can test both framework-free TypeScript and a React component without changing the static production model. Next.js is the most informative all-React comparison. Vite/vanilla is the correct simplicity control, while Preact and SvelteKit are viable lightweight alternatives but do not currently unlock a uniquely valuable terminal library.

Vercel hosting does not force this choice. Vercel documents first-class support for Next.js, SvelteKit, Astro, and Vite, and Git integration supplies preview deployments across frameworks. [Vercel frameworks](https://vercel.com/docs/frameworks)

## Accessibility, keyboard, motion, and addressability contract

Regardless of framework, the prototype should implement the same contract so the comparison is fair:

1. Render a persistent command list as `<nav>` containing real `<a href="/projects/">` or `<a href="#projects">` links. JavaScript may intercept activation to append/reveal transcript output, but the destination must remain navigable without interception.
2. Use `<button>` only for actions that do not naturally navigate, such as clearing transcript history or toggling optional help. Do not make a generic `<div>` keyboard-clickable.
3. Keep each substantive section in the initial HTML. The enhanced transcript may show a second view or scroll to the canonical section, but generated claims must not exist only in client state.
4. Give the appended transcript a stable accessible name and a polite announcement strategy such as a `role="log"` region. The ARIA `log` role is defined for sequentially appended information and has an implicit polite live-region setting. Do not move focus on every command; preserve the user's focus unless navigation intentionally changes it. [WAI-ARIA `log` role](https://www.w3.org/TR/wai-aria-1.2/#log)
5. Support Tab/Shift+Tab and native activation first. If arrow-key list navigation is added, use a tested composite widget (`cmdk`) or implement the relevant WAI-ARIA pattern completely; do not remove normal Tab access to the persistent links.
6. Store selected section in a real route or fragment. On initial load, render/locate that content; on selection, update history so Back/Forward works; never make transcript memory the only address.
7. Under `@media (prefers-reduced-motion: reduce)`, disable cursor blink, typewriter animation, smooth auto-scroll, and animated transcript insertion. Content should appear immediately. The CSS media query exists specifically to detect a user's request to minimize non-essential motion. [MDN: `prefers-reduced-motion`](https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-reduced-motion)
8. Restore a high-contrast `:focus-visible` treatment after any terminal stylesheet reset. WCAG requires keyboard functionality and a visible focus indicator. [WCAG 2.2: Keyboard](https://www.w3.org/WAI/WCAG22/Understanding/keyboard), [WCAG 2.2: Focus Visible](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible)
9. On narrow screens, allow the terminal frame to become an ordinary vertical document. Avoid fixed character-grid widths and global `word-break: break-all`; reserve horizontal scrolling for code-like material.

This contract makes the no-JS case intentionally less theatrical, not incomplete: it is the same portfolio as linked static sections, while JavaScript adds the transcript metaphor.

## Repository JSON and Portfolio Maintainer integration

All credible options can preserve GitHub as the source of truth and avoid a production API:

- Import `_data/profile.json`, `_data/generated/projects.json`, and `_data/generated/recent-work.json` during the site build.
- Render their public content into static HTML and, if useful for enhancement, emit a small serialized command index. Do not require the browser to fetch the JSON before showing core content.
- Keep the existing deterministic schema/invariant validation in the build. The framework is a renderer, not a replacement for the Portfolio Maintainer's generated-content contract.
- Keep generated JSON paths stable during initial migration or update the maintainer and tests in the same implementation change; do not add a database or CMS merely to suit a framework.
- Preserve source links/evidence in the rendered project and Maintainer views so the agentic transparency decision survives the presentation rewrite.

Astro and Vite explicitly support direct JSON imports. SvelteKit inherits Vite's build pipeline. In Next static export, local data can be consumed by build-time Server Components; static Route Handlers can also generate JSON output at build time. [Astro imports](https://docs.astro.build/en/guides/imports/#json), [Vite JSON](https://vite.dev/guide/features.html#json), [Next static Route Handlers](https://nextjs.org/docs/app/guides/static-exports#route-handlers)

One repository-specific implementation constraint is already visible: `src/maintainer/site.ts` currently rejects any `<script>` tag as an unsafe executable payload. The user has now authorized JavaScript/React/TypeScript where useful, so implementation must replace that blanket check with a build-output/content-safety rule appropriate to bundled first-party scripts. This research branch does not change that validator.

## Prototype matrix and decision evidence to collect

Build the same narrow slice in each shortlisted prototype: hero/identity, command choices for `about`, `experience`, `projects`, `recent-work`, and `maintainer`, one generated Project Profile, one Recent Work entry, URL/fragment restoration, keyboard selection, no-JS fallback, and reduced-motion mode.

| Prototype | What it should answer | Required measurements/checks |
| --- | --- | --- |
| **Astro + native TS + WebTUI** | Is a small enhancement enough, with no React dependency? Does WebTUI save meaningful design time after accessibility overrides? | Built JS/CSS transfer size; initial HTML completeness; Tab/focus behavior; links with JS disabled; hash/Back behavior; narrow viewport; reduced motion. |
| **Astro + React island + `cmdk` + WebTUI** | Does search/arrow navigation materially improve discoverability? Can the React island stay isolated and preserve native link fallback? | Island JS size; hydration behavior; screen-reader announcement; `cmdk` keyboard behavior; fallback link duplication/clarity; same responsive/motion checks. |
| **Next static export + React + `cmdk` + WebTUI** | Does the all-React composition and ecosystem make implementation simpler enough to justify the broader framework/runtime? | Output HTML per route; client JS size; static-export warnings; route refresh/404 behavior on Vercel; same accessibility/no-JS/motion checks. |
| **Optional Vite/vanilla control** | Is extending the current custom build script actually simpler than adopting a static generator? | Amount of custom generation code; JSON/schema integration; multi-page/hash behavior; build and preview configuration; same browser checks. |

The framework decision should be made from these artifacts and measurements, not from Vercel plan availability or framework popularity. Vercel supports every shortlisted deployment shape; the real choice is how much frontend runtime and custom build logic the portfolio benefits from.

## Decision-ready conclusions

- **Use an existing terminal design library:** prototype WebTUI, importing it selectively and overriding its focus/wrapping defaults. Keep Terminal.css as a lower-complexity visual reference.
- **Use JavaScript where it improves the experience:** a small TypeScript enhancement is fully compatible with static-first/no-JS requirements.
- **Use React where a React library earns it:** test `cmdk` in an Astro island and in a Next static export. React is allowed, but should be justified by interaction/design leverage rather than Vercel alone.
- **Do not use a terminal emulator:** xterm.js is excellent at a different job. `react-console-emulator` and similar pseudo-shell components also conflict with the predefined, clickable-command decision.
- **Prefer build-time JSON integration:** render Portfolio Maintainer output into HTML and preserve the current repository-backed contract; no browser API or production backend is needed.
- **Keep accessibility as a prototype gate:** no option is accepted until the same native-link fallback, visible focus, keyboard, transcript announcement, reduced-motion, responsive, and URL-restoration checks pass.
- **Keep the final architecture open:** the three primary prototypes above create the evidence needed to decide between minimal TypeScript, a bounded React island, and an all-React static export without committing the Wayfinder map prematurely.
